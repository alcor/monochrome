Retry policies

A retry policy decides what Quill does with a job whose handler throws. By default a job is tried 5 times, with a delay that doubles after each failure, and is moved to the dead-letter queue after the last attempt. A policy is set per queue and can be overridden per job.

Retries are counted per job, not per worker. A job that fails on one worker and is picked up by another keeps its count, because the count is stored with the job in quill_jobs.attempts.

Configuring a policy

Pass retry when you declare the queue. Every field is optional; the values below are the defaults.

const queue = quill.queue('email', {
  retry: {
    attempts: 5,
    backoff: 'exponential',
    baseDelayMs: 1000,
    maxDelayMs: 60000,
    jitter: 0.2,
  },
});

With these values the delays are 1, 2, 4 and 8 seconds, each moved by up to 20% in either direction so that jobs which failed together do not retry together.

Backoff strategies

Delay before attempt n, with a base delay of 1 second
StrategyAttempt 2Attempt 3Attempt 4
fixed1 s1 s1 s
linear1 s2 s3 s
exponential1 s2 s4 s

No delay is longer than maxDelayMs, which defaults to 60 seconds. An exponential policy with 12 attempts therefore waits 60 seconds from the eighth attempt on.

Errors that should not be retried

Throw quill.Fatal to send a job straight to the dead-letter queue. Use it for failures that another attempt cannot fix, such as a payload that does not parse.

queue.process(async job => {
  const user = await users.find(job.data.userId);
  if (!user) throw new quill.Fatal('no such user');
  await mailer.send(user.email, job.data.template);
});
  • A Fatal error counts as one attempt in the metrics.
  • A handler that times out is retried like any other failure. The default timeout is 30 seconds.
  • A worker that is killed mid-job does not use up an attempt. The job becomes visible again after its lease of 45 seconds runs out.

Observing retries

Each retry emits a job.retry event with the attempt number and the delay. The backoff table above gives the delay you should expect to see. In version 3.2 and later the event also carries the error's class name.
